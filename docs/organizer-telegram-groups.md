# Telegram-заявки организатору

В кабинете организатора откройте **Настройки → Уведомления → Telegram для заявок**.
Выберите группу или личный аккаунт. Настройка действует на все собственные
UUID-события этого организатора, с афиши и из приложения.

1. Добавьте [@vshageapp_bot](https://t.me/vshageapp_bot?startgroup=true) в рабочую группу.
2. Разрешите боту отправлять сообщения. Читать всю переписку ему не требуется;
   отключать privacy mode не нужно.
3. Для группы скопируйте числовой `chat_id` **вместе со знаком минус** и сохраните.
   Для обычных групп это, например, `-5177118016`; супергруппы часто начинаются с `-100`.
4. Для личного аккаунта откройте @vshageapp_bot с аккаунта получателя,
   нажмите «Запустить» и сохраните положительный числовой ID аккаунта.
   `@username` не заменяет ID личного чата.

Пустое поле отключает получателя. Уведомления владельцу ВШаге сохраняются.
В группу отправляются название события, имя, все оставленные контакты,
дата заявки по Москве, пометка «заявка через ВШаге» и необязательное интро `about`.
Другие ответы, дата рождения и внутренние ID в текст сообщения не попадают.

Если ID неизвестен, оператор с доступом к боту может прочитать `message.chat.id`
в полученном обновлении Telegram после команды, адресованной боту в группе.
Если бот получает обновления webhook-ом, используйте его обработчик/журнал:
не отключайте webhook ради `getUpdates`. Методы описаны в
[Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

## Совместимость и проверка

- API кабинета добавляет необязательное поле `telegram_chat_id`. Старый PATCH,
  в котором этого поля нет, сохраняет уже настроенный чат. Старые клиенты
  приложения (включая App Store 0.6.0) используют прежнюю форму и ответы API.
- ID может быть отрицательным (группа) или положительным (личный чат),
  с максимумом 52 значащих бита. Тип получателя в UI определяется знаком.
- Core также пишет `tg_group` при новой регистрации из приложения; sender
  повторно проверяет актуальную настройку. Повтор активной заявки не дублирует
  сообщение. Отсутствующая organizer-схема изолируется savepoint-ом.
- Миграция organizer `025` добавляет пустую настройку. Существующие события,
  заявки, уведомления владельцу и push-политика не меняются.
- Afisha ставит `tg_group` в существующую очередь внутри транзакции заявки.
  Сбой схемы/настройки изолируется savepoint-ом; сбой отправки остаётся в outbox
  с `last_error`, повтором и записью в лог. Ошибка группы не задерживает владельца
  или другую группу. Смена/удаление настройки отзывает старые доставки.
- PostgreSQL-тесты проверяют сохранение настройки, старый PATCH, отключение,
  разделение организаторов, rollback, ошибку Telegram, повтор, отзыв и отсутствие
  миграции. HTTP-транспорт в этих тестах подменён; реальная доставка проверяется
  отдельной заявкой через опубликованную страницу.

## Выкатка и откат

Порядок: migration `025` → organizer-api → afisha-backend → интерфейсы.
Старые настройки по умолчанию пусты; рассылки задним числом нет.

При откате **afisha-backend** старый отправщик не знает `tg_group` и может
переслать JSON владельцу. Сначала сохраните снимок настроек и очистите
`telegram_chat_id`, затем дождитесь завершения текущей отправки. Сохраните
неотправленные строки `channel='tg_group'` в отдельную резервную таблицу и
удалите из рабочей очереди только эти сохранённые строки, после чего смените
образ. Миграцию не откатывайте: дополнительная колонка старым клиентам не мешает.
При возврате нового образа восстановите настройки; очередь из резервной таблицы
восстанавливайте только после проверки актуальности получателей.
